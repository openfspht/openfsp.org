---
title: Implémenter OpenFSP côté opérateur
description: Parcours de lecture, surface HTTP et vérification de conformité pour un fournisseur qui veut exposer OpenFSP nativement.
---

Implémentez le contrat OpenFSP dans votre système pour recevoir directement les demandes des applications marchandes. Les SDK Kotlin, Java et TypeScript appellent cette même API. Chaque marchand garde son compte, ses clés et son contrat chez vous.

Cette page donne le plan de travail et les tests. Les obligations elles-mêmes sont dans la [spécification](/fr/docs/spec).

## Lire le contrat dans l'ordre

| Étape                             | Décision à prendre                                                                                                 | Référence                                                                                     |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| Identifier la couche traitée      | Distinguer intégration marchande, traduction d'API et règlement entre opérateurs.                                  | [Architecture de la norme](/fr/docs/architecture) et [décision 0001](/fr/docs/decisions#0001) |
| Représenter un paiement           | Montant entier en centimes de gourde, identifiants opaques, référence du marchand, horodatages et états terminaux. | [Modèle de données](/fr/docs/spec/data-model), [cycle de vie](/fr/docs/spec/lifecycle)        |
| Exposer les échanges              | Création, lecture, synchronisation, erreurs et reprise après coupure.                                              | [API des paiements](/fr/docs/spec/payments-api), [idempotence](/fr/docs/spec/idempotency)     |
| Annoncer les possibilités réelles | Découverte, capacités optionnelles et limites, sans émulation de fonction absente.                                 | [Capacités](/fr/docs/spec/capabilities)                                                       |
| Authentifier et notifier          | Clés, portées, publication des clés de signature, vérification et livraison des événements.                        | [Authentification](/fr/docs/spec/authentication), [webhooks](/fr/docs/spec/webhooks)          |
| Vérifier le périmètre applicable  | Cible `native-operator`, Core et profils correspondant aux capacités annoncées.                                    | [Conformité 5.7](/fr/docs/spec/conformance#5.7)                                               |

Les chapitres existants nomment souvent la cible passerelle. Pour l'opérateur natif, lisez les exigences à travers la [règle de portée 5.7](/fr/docs/spec/conformance#5.7), et non par remplacement automatique des mots. Les contraintes de traduction d'une API tierce ne deviennent pas des obligations de déployer cette traduction.

## Préparer la surface HTTP

| Surface                                                   | Rôle                                                                                        | Point d'attention pour la cible native                                                                                                    |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `/.well-known/openfsp-configuration`                      | Découverte publique de l'émetteur, des points d'accès, des méthodes et des clés de webhook. | Lisez la [structure de configuration](/fr/docs/spec/capabilities#3.1) et les [clés de signature](/fr/docs/spec/webhooks#6.1.1).           |
| `GET /v1/capabilities`                                    | Capacités et limites effectivement exposées.                                                | Un opérateur natif annonce un seul opérateur : lui-même, sous son identifiant enregistré ([3.2.6](/fr/docs/spec/capabilities#3.2.6)).     |
| `POST /v1/payments`                                       | Création selon le contrat, avec clé d'idempotence.                                          | Respecter le format, les refus, les rejouements et les effets inconnus ; ne pas traiter une création sans réponse comme un échec certain. |
| `GET /v1/payments/{id}` et `GET /v1/payments?reference=…` | Lecture du paiement et récupération après perte d'une réponse.                              | Le marchand connaît sa référence avant l'appel ; il ne doit pas avoir besoin de reconstruire un identifiant opaque.                       |
| `POST /v1/payments/{id}/synchronize`                      | Synchronisation de l'état selon le contrat.                                                 | Lire les règles applicables à la cible native avec le cycle de vie et les capacités annoncées.                                            |
| Relevés et notifications                                  | Fonctions conditionnées par les capacités correspondantes.                                  | Une fonction réservée ou non prise en charge ne doit pas être présentée comme disponible.                                                 |

Les URL ci-dessus désignent la surface normative. Les clients devraient lire les URL publiées dans le document de découverte plutôt que les reconstruire ([3.1.3](/fr/docs/spec/capabilities#3.1.3)). L'[identifiant `provider`](/fr/docs/registry) reste distinct du nom commercial affiché.

## Traiter la notification d'un paiement

Pour les appels qui utilisent le `callback_url` prévu par le contrat, vérifiez les conditions de l'[API 5.1.8](/fr/docs/spec/payments-api#5.1.8). Les tests natifs contrôlent notamment la livraison d'un `payment.succeeded` signé, les clés Ed25519 publiées et le refus d'un `callback_url` HTTP hors des exceptions de bouclage.

Ne prenez pas le comportement du simulateur pour une extension implicite du protocole. Les événements, leur signature, leur ordre et leur déduplication suivent les [webhooks](/fr/docs/spec/webhooks) ; le détail des tests natifs se trouve en [5.7.1](/fr/docs/spec/conformance#5.7.1).

## Observer une implémentation native simulée

Le dépôt de référence contient `mock_openfsp`, un opérateur fictif qui expose lui-même OpenFSP. Il permet d'étudier et de tester la connexion directe, sans passerelle.

Depuis le dépôt [openfsp](https://github.com/openfspht/openfsp), avec les prérequis du [démarrage rapide](/fr/docs/quickstart#2), utilisez deux terminaux :

```bash title="Terminal 1 : opérateur simulé"
make simulator
```

```bash title="Terminal 2 : suite contre la cible native"
make validate-native
```

La cible par défaut est `http://127.0.0.1:8090/mock_openfsp`. Le rapport est écrit dans `backend/validator/infrastructure/build/conformance-report-native.json`. La commande utilise les clés de test publiées par le simulateur et démarre le récepteur de webhooks de la suite sur le port 8098, valeur par défaut du Makefile (`VALIDATE_NATIVE_WEBHOOK_PORT`). Cette exécution ne lance pas la passerelle.

Les [sources de l'opérateur natif simulé](https://github.com/openfspht/openfsp/tree/main/backend/simulator/infrastructure/src/main/kotlin/org/openfsp/simulator/dialects/openfsp) et le [Makefile](https://github.com/openfspht/openfsp/blob/main/Makefile) permettent de vérifier le comportement et la commande.

## Tester votre implémentation

Préparez une instance de test dédiée, ses clés de test et les capacités que vous souhaitez revendiquer. Construisez le CLI depuis le dépôt de référence :

```bash
cd backend
./gradlew :validator:infrastructure:bootJar
cd ..
```

La commande suivante lance la suite contre votre instance. Remplacez `operator.example` et renseignez les clés de votre environnement de test :

```bash
java -jar backend/validator/infrastructure/build/libs/app.jar validate \
  --target native-operator \
  --base-url https://operator.example \
  --api-key "$OPENFSP_NATIVE_TEST_KEY" \
  --conformance conformance \
  --report conformance-report-native.json \
  --input "statements-key=$OPENFSP_STATEMENTS_KEY" \
  --input "restricted-key=$OPENFSP_SECOND_PRINCIPAL_KEY" \
  --input "revoked-key=$OPENFSP_REVOKED_KEY" \
  --input "expired-key=$OPENFSP_EXPIRED_KEY" \
  --webhook-port 8098 \
  --webhook-url https://receiver.example/webhooks
```

| Entrée           | Clé                                                                    |
| ---------------- | ---------------------------------------------------------------------- |
| `statements-key` | Une clé avec la portée `statements:read`.                              |
| `restricted-key` | Une clé d'un autre principal avec `payments:read` et `payments:write`. |
| `revoked-key`    | Une clé que vous avez révoquée.                                        |
| `expired-key`    | Une clé arrivée à expiration.                                          |

Le CLI n'a pas de port de webhook par défaut : sans `--webhook-port`, il ne démarre aucun récepteur et le test du `payment.succeeded` signé ne s'exécute pas. `--webhook-url` est l'adresse HTTPS publique qu'appelle votre instance, redirigée vers ce port ; sans elle, le récepteur annonce `http://127.0.0.1:8098/webhooks`, que seule une instance locale peut joindre.

Ne pointez pas `make validate-native` vers un opérateur réel : ses valeurs par défaut et ses entrées sont celles de `mock_openfsp`.

Certains scénarios exigent que vous produisiez un refus, une expiration ou une transition. Sans contrôle automatisé adapté, la suite les déclare assistés et indique l'action requise ([configuration de la suite](/fr/docs/spec/conformance#4)).

## Lire et publier le résultat

`make validate-native` se termine avec le code 0 quand Core n'est incomplet qu'à cause de scénarios assistés : lisez donc le rapport plutôt que le code de sortie. Les verdicts et les niveaux sont définis en [conformité 6](/fr/docs/spec/conformance#6).

Publiez une affirmation limitée à ce périmètre, accompagnée du rapport, de la configuration expurgée et des versions. Une [attestation signée](/fr/docs/verify) authentifie les résultats d'une exécution ; elle ne certifie pas un produit.
