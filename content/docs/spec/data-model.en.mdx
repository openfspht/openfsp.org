---
title: Data model
description: Shared types, JSON representations and constraints on exchanged data.
---

The interface contract uses integer amounts, an explicit currency and opaque identifiers. [Decision 0002](/en/docs/decisions#0002) documents the constraints and rationale for these representations.

## 1. Types

| Type                | JSON form                     | Example                                                                 |
| ------------------- | ----------------------------- | ----------------------------------------------------------------------- |
| `Money`             | object                        | `{"amount": 125000, "currency": "HTG"}`                                 |
| `Currency`          | string, single value `HTG`    | `"HTG"`                                                                 |
| `PhoneNumber`       | string, E.164                 | `"+50934567890"`                                                        |
| `ResourceId`        | opaque string                 | `"pay_01J9ZK3QF8XN2M7VYB4C6D8E0G"`                                      |
| `Reference`         | string chosen by the merchant | `"INV-2026-00184"`                                                      |
| `Timestamp`         | string, RFC 3339 UTC          | `"2026-08-17T14:32:07.412Z"`                                            |
| `Date`              | string, RFC 3339 `full-date`  | `"2026-09-28"` ([lifecycle 10.1](/en/docs/spec/lifecycle#10.1))            |
| `Fee`               | object                        | `{"amount": {"amount": 1250, "currency": "HTG"}, "bearer": "merchant"}` |
| `Metadata`          | object of strings             | `{"order_id": "184"}`                                                   |

## 2. JSON conventions

**2.1.** Request and response bodies use JSON (RFC 8259) with UTF-8 encoding.

**2.2.** Field names use `lower_snake_case` and MUST NOT be changed within the same major version.

**2.3.** The client MUST ignore any unknown response field.

**2.4.** The server MUST reject any request body containing an unknown field with `400` and identify the field concerned.

**2.5.** For an OPTIONAL field, omission and the value `null` are equivalent. Implementations SHOULD omit the field rather than transmit `null`. A REQUIRED field MUST NOT have the value `null`.

**2.6.** Strings, except for `Metadata` values (9.3), SHOULD be normalised to NFC before storage and comparison. Length limits are measured in Unicode code points.

**2.7.** Boolean and numeric values use their native JSON types rather than string representations.

## 3. `Money`

**3.1.** The fields `amount` and `currency` are REQUIRED.

**3.2.** The `amount` field represents an integer number of HTG cents: `125000` corresponds to 1,250.00 HTG.

**3.3.** The `amount` field MUST be represented as a JSON number without a fractional part or exponent.

**3.4.** The value of `amount` MUST lie in the inclusive range from -(2⁵³ - 1) to 2⁵³ - 1. Implementations MUST reject values outside this range.

**3.5.** An implementation MUST NOT represent an amount in a form that could lose a cent, even temporarily; fractional gourde values are excluded. A binary64 floating-point type MAY represent the integer number of cents because every integer in the range defined in 3.4 is exact in that type. All arithmetic on that number MUST preserve integer values within the range.

**3.6.** Unless another specification provides otherwise, a request amount MUST be strictly positive. The server MUST reject a zero amount.

**3.7.** Two `Money` values are equal when their `amount` values are equal.

**3.8.** An implementation MUST NOT apply rounding to an amount.

## 4. Currency

**4.1.** The gourde is the only supported currency: `currency` MUST equal `"HTG"` (ISO 4217, exponent 2). Any other value MUST be rejected with `invalid-field`.

**4.2.** Adding support for a currency requires a decision record.

## 5. Phone number

**5.1.** The number follows E.164 and the expression `^\+[1-9]\d{1,14}$`.

**5.2.** Valid example: `"+50934567890"`. Invalid examples: `"34567890"`, `"+509 34 56 78 90"`, `"+509-3456-7890"` and `"050934567890"`.

**5.3.** The server MUST NOT infer a country code from a national number and MUST reject values that do not conform to 5.1. An SDK MAY convert local input to E.164. A merchant interface MAY display a Haitian number as `+509 40 00 0000`; the exchanged value retains E.164 format (`+50940000000`).

**5.4.** Syntactic validity MUST NOT be treated as verification of the number.

## 6. Identifiers

### 6.1. `ResourceId`

**6.1.1.** The identifier contains 1 to 64 characters from `A-Za-z0-9_-`. It is assigned by the server at creation and remains immutable.

**6.1.2.** The identifier is opaque: the client MUST NOT parse it, infer ordering from it or construct a value.

**6.1.3.** Implementations SHOULD generate a version 7 UUID (RFC 9562). Any other generator satisfying 6.1.1 and 6.1.4 is permitted.

**6.1.4.** The identifier MUST NOT be predictable. Sequential integers and counters are prohibited.

**6.1.5.** A type prefix followed by an underscore (`pay_`, `rfd_`) is RECOMMENDED. This prefix belongs to the opaque value.

### 6.2. `Reference`

**6.2.1.** The reference contains 1 to 128 characters from `A-Za-z0-9._:/-`. It is supplied by the merchant at creation and remains immutable.

**6.2.2.** A `Reference` MUST be unique among resources of the same type within a merchant account, regardless of the principal that created them. The server MUST reject creation using an existing reference.

**6.2.3.** The `Reference` is the primary correlation key, particularly for recovering a payment when its creation received no response.

**6.2.4.** The `Reference` MUST NOT include personal data or a secret identifier.

**6.2.5.** The relationship with `Idempotency-Key` is defined in [idempotency 6](/en/docs/spec/idempotency#6).

### 6.3. `IdempotencyKey`

**6.3.1.** The key contains 1 to 255 characters from `A-Za-z0-9_-` and is transmitted in the `Idempotency-Key` header. Its semantics are defined in [Idempotency](/en/docs/spec/idempotency).

## 7. Timestamp

**7.1.** Timestamps use the RFC 3339 `date-time` format in UTC with an uppercase `Z`: `"2026-08-17T14:32:07.412Z"`.

**7.2.** Numeric offsets, a lowercase `z` suffix and dates without a time MUST be rejected.

**7.3.** Seconds are REQUIRED; fractional seconds down to milliseconds are OPTIONAL. The client MUST accept these fractions and the server MUST NOT require them.

**7.4.** Timestamps MUST NOT define a total order across events. The client MUST NOT derive a sequence from them.

## 8. `Fee`

**8.1.** The object describes fees applied by the provider to a payment.

| Field    | Type    | Presence | Notes                  |
| -------- | ------- | -------- | ---------------------- |
| `amount` | `Money` | REQUIRED | In HTG.                |
| `bearer` | string  | REQUIRED | `merchant` or `payer`. |

**8.2.** An absent `Fee` means fees are unknown; zero fees are represented by a zero amount. The client MUST NOT display absent fees as zero or calculate them by subtraction.

**8.3.** The `bearer` field identifies the party that bore the fees according to the provider. The server MUST NOT allow the client to set it.

**8.4.** The server MUST NOT defer a terminal transition while waiting for fee data or assign an unestablished fee value.

**8.5.** A server unable to report a provider’s fees MUST NOT declare `payments.fee` for that provider.

## 9. `Metadata`

**9.1.** This OPTIONAL object maps strings to strings and accompanies every resource representation. The client supplies it at creation; the server MAY add its own keys under 9.4.

**9.2.** The object contains at most 20 keys. Each key contains 1 to 40 characters from `A-Za-z0-9_.-`; each value contains at most 500 characters. Non-string values are invalid.

**9.3.** The server MUST store and return the client’s keys unchanged, MUST NOT remove them and MUST NOT assign semantics to them.

**9.4.** The server documents the keys it adds. It MUST NOT add a key already supplied by the client. Server keys are excluded from the limits in 9.2.

**9.5.** Merchants SHOULD NOT include personal data in this object and MUST NOT include secret identifiers.

## 10. Security

**10.1.** Phone numbers MUST NOT appear in any log other than the audit log ([authentication 9](/en/docs/spec/authentication#9)), or in error messages or telemetry.

**10.2.** The server SHOULD state in its documentation that metadata is not encrypted at rest unless the operator applies such encryption.
