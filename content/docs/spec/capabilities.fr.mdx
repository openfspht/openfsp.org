title: Capacités et bornes
description: Déclarer et découvrir les fonctions et limites réelles de chaque opérateur compatible.
---

Je rends les opérations disponibles et les plafonds du compte consultables avant la création du paiement. Je motive le refus de l’émulation dans la [décision 0005](/fr/docs/decisions#0005).

## 1. Capacité

**1.1.** Une capacité est une fonctionnalité nommée, prise en charge ou non pour un opérateur
donné.

**1.2.** Les capacités sont déclarées par opérateur, jamais pour le serveur entier.

**1.3.** Un serveur DOIT n'annoncer une capacité pour un opérateur que si cet opérateur exécute
l'opération lui-même. Il NE DOIT PAS annoncer une capacité obtenue par émulation,
approximation ou composition d'autres opérations.

**1.4.** Capacité `payments` : [API 2.1](/fr/docs/spec/payments-api#2.1).

## 2. Noms et registre

**2.1.** Un nom de capacité correspond à `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$` : domaine,
puis opération.

**2.2.** Registre. Un nom _réservé_ n'a pas encore de spécification et NE DOIT PAS être
annoncé. Un nom _retiré_ NE DOIT PAS être annoncé et n'est jamais réattribué (2.5).

| Nom                            | Statut                | Sens                                                                                                                       |
| ------------------------------ | --------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `payments`                     | spécifié, obligatoire | Créer, lire, synchroniser un paiement ([API](/fr/docs/spec/payments-api)).                                                 |
| `payments.lookup`              | spécifié              | Consultation faisant foi de l'état chez l'opérateur (5).                                                                   |
| `payments.statement`           | spécifié              | Relevé quotidien du compte marchand chez l'opérateur, lisible par le client ([cycle de vie 10](/fr/docs/spec/lifecycle#10)). |
| `payments.fee`                 | spécifié              | L'opérateur communique les frais ([modèle de données 8](/fr/docs/spec/data-model#8)).                                      |
| `payments.refund`              | réservé               | Remboursement d'un paiement capturé.                                                                                       |
| `payments.capture`             | réservé               | Autorisation et capture séparées.                                                                                          |
| `payments.cancel`              | réservé               | Annulation avant achèvement.                                                                                               |
| `payments.proximity_cpm`       | réservé               | Résolution native de jetons présentés par le payeur.                                                                       |
| `confirmation_requests`        | réservé               | Confirmation minutée par le payeur.                                                                                        |
| `confirmation_requests.cancel` | réservé               | Retrait d'une demande avant réponse du payeur.                                                                             |
| `transfers`                    | réservé               | Envoi de fonds à un bénéficiaire.                                                                                          |
| `webhooks.emit`                | spécifié              | Événements signés vers le client ([webhooks](/fr/docs/spec/webhooks)).                                                     |
| `webhooks.verify`              | retiré                | Aucun.                                                                                                                     |
| `webhooks.per_payment_url`     | spécifié              | L'opérateur accepte une `callback_url` à la création et y livre les événements de ce paiement ([API 5.1.8](/fr/docs/spec/payments-api#5.1.8)). |

**2.3.** Ajouter un nom exige une décision écrite. Un ajout ne rompt pas la compatibilité (4.3).

**2.4.** Un serveur PEUT annoncer des noms hors registre, préfixés d'un nom DNS inversé
qu'il contrôle (`com.example.payments.instalments`), et NE DOIT PAS inventer de noms non
préfixés.

**2.5.** Les capacités ne sont pas versionnées : un changement de sens exige un nouveau nom.

**2.6.** Le serveur DOIT utiliser l'identifiant enregistré de chaque opérateur
([registre](/fr/docs/registry)).

**2.7.** Un identifiant d'opérateur s'enregistre par pull request sur le registre, sans décision écrite.

**2.8.** Les identifiants sont permanents ; un opérateur renommé reçoit un nouvel identifiant
et l'ancien est marqué remplacé.

## 3. Découverte

### 3.1. Document de configuration

```
GET /.well-known/openfsp-configuration
```

Non authentifié (RFC 8615). Je reprends la forme de la découverte OpenID Connect : des URL
absolues suffixées `_endpoint` ou `_uri`, et des listes suffixées `_supported`.

```json
{
  "issuer": "https://api.example",
  "protocol_version": "0.1.0",
  "api_base": "https://api.example/v1",
  "payments_endpoint": "https://api.example/v1/payments",
  "capabilities_endpoint": "https://api.example/v1/capabilities",
  "statements_endpoint": "https://api.example/v1/statements",
  "statement_entries_endpoint": "https://api.example/v1/statement_entries",
  "webhook_keys": [
    { "kid": "whk_06GWCT5DMSTMH111XG1Q28R4MW", "kty": "OKP", "crv": "Ed25519", "alg": "EdDSA", "use": "sig", "x": "…", "openfsp_status": "active" }
  ],
  "authentication_methods_supported": ["bearer"],
  "scopes_supported": ["capabilities:read", "payments:read", "payments:write", "statements:read"],
  "capabilities_supported": ["payments", "payments.lookup", "payments.statement", "webhooks.emit", "webhooks.per_payment_url"],
  "webhook_signature_algorithms_supported": ["ed25519"]
}
```

**3.1.1.** Le document NE DOIT PAS révéler les opérateurs utilisés, ni d'information sur le
marchand, ni la version du logiciel du serveur, ni l'interface d'administration.

**3.1.2.** `protocol_version` est la version de spécification visée. Un client NE DOIT PAS en
déduire de capacité.

**3.1.3.** `issuer` est l'URL publique du serveur, sans barre oblique finale. Un client
DEVRAIT lire les points d'accès dans ce document plutôt que de les construire.

**3.1.4.** `capabilities_supported` liste les noms de capacité (2) que le logiciel du
serveur sait servir. Cette liste NE DOIT PAS dépendre des opérateurs configurés. Ce qu'un
opérateur annonce réellement se lit dans `/v1/capabilities` (3.2).

**3.1.5.** `webhook_keys` contient les clés publiques de signature des webhooks
([webhooks 6.1](/fr/docs/spec/webhooks#6.1)). C'est leur seul point de publication.

### 3.2. Capacités

```
GET /v1/capabilities
```

Authentifié.

```json
{
  "protocol_version": "0.1.0",
  "providers": [
    {
      "id": "moncash",
      "display_name": "MonCash",
      "capabilities": ["payments", "payments.lookup"],
      "payments": {
        "next_actions": ["redirect"],
        "payer_required": false,
        "return_url_required": true,
        "expiry_guaranteed": false,
        "locales": []
      }
    }
  ]
}
```

**3.2.1.** Champs d'un opérateur :

| Champ          | Type               | Présence    | Notes                                                     |
| -------------- | ------------------ | ----------- | --------------------------------------------------------- |
| `id`           | chaîne             | OBLIGATOIRE | Identifiant enregistré ; égal à `provider` d'un paiement. |
| `display_name` | chaîne             | OBLIGATOIRE | Affichage, pas un identifiant.                            |
| `logo_url`     | chaîne             | FACULTATIF  | URL absolue d'un logo à afficher près de `display_name`.  |
| `capabilities` | tableau de chaînes | OBLIGATOIRE | Contient toujours `payments`.                             |
| `payments`     | objet              | OBLIGATOIRE | 3.2.2.                                                    |

**3.2.2.** Objet `payments` :

| Champ                 | Type               | Sens                                                                                          |
| --------------------- | ------------------ | --------------------------------------------------------------------------------------------- |
| `next_actions`        | tableau de chaînes | Types de `next_action` produits ([API 4.2](/fr/docs/spec/payments-api#4.2)).                  |
| `payer_required`      | booléen            | `payer` exigé à la création.                                                                  |
| `return_url_required` | booléen            | `return_url` exigée à la création.                                                            |
| `expiry_guaranteed`   | booléen            | Garantie du [cycle de vie 5.3](/fr/docs/spec/lifecycle#5.3) (b).                              |
| `limits`              | objet              | FACULTATIF. Bornes de montant (6.4).                                                          |
| `locales`             | tableau de chaînes | Valeurs de `locale` prises en charge pour la page du payeur ([API 5.1.7](/fr/docs/spec/payments-api#5.1.7)). |

**3.2.3.** `expiry_guaranteed` DOIT valoir `false` sauf si l'opérateur garantit qu'un paiement
non achevé à `expires_at` ne s'achèvera jamais.

**3.2.4.** La réponse DEVRAIT porter `Cache-Control` avec un `max-age` d'une heure au plus.

**3.2.5.** Par exception au 1.3, `webhooks.emit` figure dans la liste de chaque opérateur pour
lequel le serveur émet des événements.

## 4. Obligations

**4.1.** Un client NE DOIT PAS invoquer une opération dont la capacité n'est pas annoncée pour
l'opérateur choisi.

**4.2.** Un client DOIT traiter `capability-not-supported` à tout moment, et DEVRAIT alors
relire les capacités.

**4.3.** Un client DOIT ignorer un nom de capacité inconnu.

**4.4.** Le serveur DOIT rejeter avec `capability-not-supported` toute opération dont il
n'annonce pas la capacité, même s'il peut l'exécuter.

**4.5.** Le serveur PEUT détecter qu'un opérateur a suspendu une capacité ; s'il le
détecte, il NE DOIT PAS l'annoncer.

## 5. `payments.lookup`

**5.1.** `payments.lookup` annonce une consultation faisant foi de l'état courant chez
l'opérateur.

**5.2.** Si elle est annoncée, la synchronisation ([API 5.3](/fr/docs/spec/payments-api#5.3)) DOIT lire
l'état chez l'opérateur.

**5.3.** Sinon, la synchronisation DOIT renvoyer `capability-not-supported` et NE DOIT PAS
renvoyer l'état stocké comme s'il avait été relu.

**5.3.1.** Exception : un paiement terminal est renvoyé inchangé en `200`
([API 5.3.3](/fr/docs/spec/payments-api#5.3.3)).

## 6. Bornes de montant

**6.1.** Les bornes d'un opérateur sont le montant minimal et le montant maximal d'une
transaction sur le compte marchand, fixés par l'opérateur pour ce marchand.

**6.2.** La façon dont le serveur connaît les bornes d'un opérateur sort du périmètre. Aucun
point d'administration n'est exigé.

**6.3.** Le serveur NE DOIT PAS inventer une borne, ni en déduire une des échecs passés.

**6.4.** L'objet `payments` d'un opérateur (3.2.2) porte un membre FACULTATIF `limits` :

```json
"limits": {
  "min_amount": { "amount": 1000, "currency": "HTG" },
  "max_amount": { "amount": 7500000, "currency": "HTG" },
  "amount_step": { "amount": 100, "currency": "HTG" }
}
```

| Champ         | Type    | Présence   | Notes                                                          |
| ------------- | ------- | ---------- | -------------------------------------------------------------- |
| `min_amount`  | `Money` | FACULTATIF | 6.5.                                                           |
| `max_amount`  | `Money` | FACULTATIF | 6.5.                                                           |
| `amount_step` | `Money` | FACULTATIF | Le montant DOIT en être un multiple. `100` : gourdes entières. |

**6.5.** Une borne absente signifie « non connue », pas « illimitée ». Un client NE DOIT PAS
l'afficher comme une absence de plafond.

**6.6.** Si `min_amount` et `max_amount` sont présents, `min_amount` DOIT être inférieur ou égal
à `max_amount`.

**6.7.** À la création ([API 5.1](/fr/docs/spec/payments-api#5.1)), le serveur DOIT rejeter un montant
inférieur à `min_amount`, supérieur à `max_amount` ou non multiple de `amount_step`, avec
`amount-out-of-range`, sans créer de paiement. La réponse porte les bornes en membres
d'extension :

```json
{
  "type": "https://openfsp.org/problems/amount-out-of-range",
  "title": "Amount out of range",
  "status": 422,
  "retryable": false,
  "effect": "none",
  "request_id": "req_01J9ZR2T4V6X8Z0B2D4F6H8K0M",
  "min_amount": { "amount": 1000, "currency": "HTG" },
  "max_amount": { "amount": 7500000, "currency": "HTG" },
  "amount_step": { "amount": 100, "currency": "HTG" }
}
```

**6.7.1.** Un montant que le [modèle de données 3.6](/fr/docs/spec/data-model#3.6) rejette (nul ou négatif)
est rejeté avec `invalid-field` avant le contrôle des bornes, même si des bornes sont déclarées.

**6.8.** `amount-out-of-range` est une erreur causée par la requête : sa réponse est enregistrée au titre de
l'[idempotence 5.1](/fr/docs/spec/idempotency#5.1). Après un changement de bornes, un client qui soumet de
nouveau la création DOIT utiliser une nouvelle `Idempotency-Key`.

**6.9.** Un paiement refusé par l'opérateur pour un plafond du payeur, ou pour une borne non
annoncée, passe à `failed` avec `limit_exceeded`
([cycle de vie 7.2](/fr/docs/spec/lifecycle#7.2)). Le serveur NE DOIT PAS le convertir en
`amount-out-of-range`.

## 7. Conformité

**7.1.** Un serveur conforme DOIT servir les deux points d'accès du 3.

**7.2.** La suite de conformité vérifie le 2.2.

**7.3.** La suite teste le 6.7 aux deux bornes (borne acceptée, borne dépassée d'un centime)
et vérifie qu'aucun paiement n'est créé.

## 8. Sécurité

**8.1.** Le document de configuration DEVRAIT être limité en débit.

**8.2.** L'annonce d'une capacité ne confère aucune autorisation : le serveur DOIT contrôler
la portée de la clé indépendamment ([authentification 6](/fr/docs/spec/authentication#6)).

**8.3.** Les bornes ne sont servies que par le point d'accès authentifié du 3.2,
jamais par le document de configuration (3.1.1).
