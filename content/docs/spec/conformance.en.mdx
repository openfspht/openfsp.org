---
title: Conformance
description: Conformance scopes, verification methods, reports and requirements for the reference mock server.
---

Conformance is defined by target, protocol version and applicable capabilities. The report records completed checks and their limitations. [Decision 0008](/en/docs/decisions#0008) explains the principles of this assessment.

## 1. Definition

**1.1.** A conformance claim identifies a triple: target, level and protocol version. An incomplete claim is not recognised; its publisher MUST NOT present it as a conformance claim.

**1.2.** Conformance applies to a particular specification version. A result obtained for one major version does not extend to another major version.

**1.3.** Conformance characterises a deployment configuration rather than source code alone.

**1.4.** The result is dated and reproducible. With the same implementation, suite version and configuration, executions MUST produce the same result (9.6).

## 2. Targets

**2.1.** Assessed targets and substitute components are defined below:

| Target | Tested                                  | Replaced by          |
| ------ | --------------------------------------- | -------------------- |
| Client | Application or SDK that calls a server. | The mock server (9). |
| Server | Implementation of the API.              | Nothing.             |

**2.2.** Client conformance covers response handling: recovery by reference, the non-authoritative nature of the return URL, idempotency-key reuse and handling a payment that remains `pending`.

**2.3.** Tests applicable to the server target are defined in section 5.

**2.4.** Each execution assesses exactly one target.

## 3. Levels

**3.1.** The **Core** level covers the base capability ([API 2](/en/docs/spec/payments-api#2)) and general requirements: data model, lifecycle, idempotency, errors, authentication, capability discovery, declared limits and rejection tests in 5.4.

**3.2.** An implementation is conforming only if it satisfies Core.

**3.3.** A profile’s name corresponds to the assessed capability. A profile MUST NOT be claimed for an undeclared capability.

| Profile                    | Capability                       | Specification                                                                    |
| -------------------------- | -------------------------------- | -------------------------------------------------------------------------------- |
| `payments.lookup`          | Authoritative lookup             | [capabilities 5](/en/docs/spec/capabilities#5)                                      |
| `payments.statement`       | Provider statement               | [statements](/en/docs/spec/lifecycle#10)                                            |
| `payments.fee`             | Fees reported by the provider    | [data model 8](/en/docs/spec/data-model#8)                                          |
| `webhooks.per_payment_url` | Events delivered to `callback_url` | [API 5.1.8](/en/docs/spec/payments-api#5.1.8)                                     |
| `webhooks.emit`            | Signed events                    | [webhooks](/en/docs/spec/webhooks)                                                  |

**3.4.** A capability specification MUST define the tests associated with its profile.

**3.5.** Failure of any Core test causes Core to fail. The suite MUST NOT report Core as passed when one of its tests has failed or express its result as a pass rate.

**3.6.** Passing all profiles defines no additional conformance level.

## 4. Execution

**4.1.** Any party may run the suite against an implementation of its choice. Execution produces the report defined in section 7.

**4.2.** When assessing a server, the suite acts as the client.

**4.3.** The suite MUST NOT require modifications, instrumentation or a test mode in the assessed implementation.

**4.4.** Only configuration is permitted: test credentials, a key with `statements:read` for 5.9 and inputs required by assisted tests under 4.7.

**4.5.** The suite controls the control interface the implementation provides (4.9). Without one, tests requiring a selected outcome are assisted under 4.7.

**4.6.** The suite MUST be runnable offline and in continuous integration without an account.

**4.7.** A test requiring operator intervention is marked as assisted, for example to revoke a key, declare limits or produce a selected outcome. The suite describes the action, the operator performs it through server administration or configuration, and the report records the assistance. This intervention is not a modification under 4.3.

### 4.8. Preparation by the server

**4.8.1.** A server MAY provide the items of 4.4 itself. It then announces the `conformance_endpoint` member in its configuration document ([capabilities 3.1.6](/en/docs/spec/capabilities#3.1.6)). The absence of this member does not affect conformance.

**4.8.2.** The suite sends a `POST` request to that URL. The optional body is a JSON object whose `webhook_url` member identifies the suite’s webhook receiver.

**4.8.3.** The server responds `201 Created` with a JSON object carrying the following members:

| Member       | Type      | Presence | Content                                                             |
| ------------ | --------- | -------- | ------------------------------------------------------------------- |
| `api_key`    | string    | REQUIRED | Active test key holding every supported scope.                      |
| `expires_at` | `Instant` | REQUIRED | Instant from which the provided items are no longer valid.          |
| `inputs`     | object    | OPTIONAL | Suite inputs, each name of 4.8.4 being associated with a text value. |
| `control_endpoint` | string | OPTIONAL | Control interface of the run (4.9).                               |

**4.8.4.** The server provides the inputs it can produce among the following. The suite ignores any other name and treats a test whose input is missing as assisted under 4.7.

| Input              | Value                                                                                              |
| ------------------ | -------------------------------------------------------------------------------------------------- |
| `restricted-key`   | Key of a second principal, with `payments:read` and `payments:write`, without `statements:read`.   |
| `statements-key`   | Key holding `statements:read`.                                                                     |
| `revoked-key`      | Key revoked for longer than the delay of [authentication 7.3](/en/docs/spec/authentication#7.3).   |
| `expired-key`      | Key whose expiry date has passed.                                                                  |
| `bounded-provider` | Identifier of a payment service declaring `min_amount`, `max_amount` and `amount_step`.            |

**4.8.5.** When `webhook_url` is provided and the server declares `webhooks.emit`, the server delivers to that URL, until `expires_at`, the events of payments created with `api_key`, for every event type. It MUST NOT deliver the events of any other payment to it.

**4.8.6.** The endpoint MUST issue only keys of the test environment. A deployment that accepts production keys MUST NOT expose it. The issued items MUST stop being valid at `expires_at`, and the keys of one call MUST NOT give access to payments created with those of another call.

**4.8.7.** The server MAY require an access code issued by its operator, sent in `Authorization: Bearer`. Without a valid code, it responds `401` with the `unauthenticated` problem. The server SHOULD limit the number of simultaneous preparations and respond `429` beyond it.

**4.8.8.** The report states that the items were provided by the server. A test run with an input provided this way is not assisted under 4.7, and the use of this endpoint is not a modification under 4.3.

### 4.9. Choice of outcomes

**4.9.1.** An implementation MAY let the suite choose the outcome of a payment. Its response of 4.8.3 then carries the `control_endpoint` member, a URL of the same origin as the issuer naming the control interface of the run.

**4.9.2.** The control interface exposes the following operations, authenticated with `api_key`:

| Operation                                                | Effect                                                                                  |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `PUT {control_endpoint}/references/{reference}/scenario` | Sets the scenario of the next payment created with this reference. Body: `{"scenario": "DECLINE"}`. |
| `GET {control_endpoint}/references/{reference}`          | Returns the state of the payment of this reference: `payment`, `settled` and `callbacks_sent`. |
| `POST {control_endpoint}/payments/{id}/resolve`          | Gives its outcome to a pending payment. Body: `{"outcome": "succeeded"}`, with `reason` on failure. |
| `POST {control_endpoint}/payments/{id}/callback`         | Triggers the held event of this payment.                                                |

**4.9.3.** Available scenarios are defined in the following table:

| Scenario             | Behaviour                                                      | Rule exercised                               |
| -------------------- | -------------------------------------------------------------- | -------------------------------------------- |
| `SUCCESS`            | Success with no added delay.         | Nominal path.                                |
| `DECLINE`            | Failure, declined.                                             | [Lifecycle 7.2](/en/docs/spec/lifecycle#7.2)    |
| `INSUFFICIENT`       | Failure, insufficient funds.                                   | [Lifecycle 7.2](/en/docs/spec/lifecycle#7.2)    |
| `TIMEOUT`            | Request accepted, no response in time: `504 provider-timeout`. | [API 5.1.6](/en/docs/spec/payments-api#5.1.6)   |
| `PENDING_FOREVER`    | Stays pending until instructed (4.9.2).                          | [Lifecycle 1.1](/en/docs/spec/lifecycle#1.1)    |
| `EXPIRE`             | Expires at the expiry time, set to one minute after creation.  | [Lifecycle 5](/en/docs/spec/lifecycle#5)        |
| `NO_CALLBACK`        | Outcome reached, no event delivered to `callback_url`.         | [Webhooks 10.2](/en/docs/spec/webhooks#10.2)    |
| `LATE_CALLBACK`      | Event delivered very late to `callback_url`.                   | [Webhooks 8.3](/en/docs/spec/webhooks#8.3)      |
| `DUPLICATE_CALLBACK` | Same event delivered several times to `callback_url`.          | [Webhooks 8.4](/en/docs/spec/webhooks#8.4)      |
| `UNKNOWN_STATUS`     | Never-seen `status` value.                                     | [Lifecycle 1.2](/en/docs/spec/lifecycle#1.2)    |
| `PROVIDER_ERROR`     | Provider-side error.                                           | [API 10.8.6](/en/docs/spec/payments-api#10.8.6) |

**4.9.4.** Scenario selection is deterministic at payment creation. No scenario occurs without explicit selection.

**4.9.5.** An additional scenario is introduced only when a specification defines behaviour that cannot otherwise be triggered.

**4.9.6.** The implementation responds `422` to a scenario it cannot produce for the payment service concerned; the suite then treats the test as assisted under 4.7.

**4.9.7.** The implementation produces the requested outcome itself. The result MUST NOT depend on the behaviour of an external payment service.

**4.9.8.** A payment whose reference received no scenario behaves as outside a conformance run.

**4.9.9.** The interface exists only in the test environment. It MUST act only on the payments created with the keys of the call of 4.8.2 and stops answering at `expires_at`.

**4.9.10.** The report states that the outcomes were chosen by the suite. A test run this way is not assisted under 4.7, and the use of this interface is not a modification under 4.3.

## 5. Content

**5.1. Shape.** Checks cover media types ([API 1.4](/en/docs/spec/payments-api#1.4)), collection envelopes ([API 1.12](/en/docs/spec/payments-api#1.12)), `Request-Id` ([API 1.8](/en/docs/spec/payments-api#1.8)), error objects ([API 10.1](/en/docs/spec/payments-api#10.1)), integer `Money` values ([data model 3](/en/docs/spec/data-model#3)), UTC timestamps ([data model 7](/en/docs/spec/data-model#7)) and unknown-field handling in requests and responses ([data model 2.3, 2.4](/en/docs/spec/data-model#2.4)).

**5.2. Lifecycle.** Tests verify that the transitions in [lifecycle 2](/en/docs/spec/lifecycle#2) are reachable, except `pending` to `canceled`, that no terminal state is left, and that `failure_reason` is present if and only if `status` is `failed`.

**5.3. Idempotency.** Tests verify replay of the stored response ([idempotency 3.2](/en/docs/spec/idempotency#3.2)), rejection of a different body with the same key ([idempotency 3.3](/en/docs/spec/idempotency#3.3)), prevention of parallel execution for a concurrent duplicate, held or rejected with `idempotency-request-in-progress` and `Retry-After` ([idempotency 3.4](/en/docs/spec/idempotency#3.4)), principal isolation ([idempotency 2.3](/en/docs/spec/idempotency#2.3)) and permanent rejection of duplicate `reference` values.

**5.4. Refusals.** Each case in the table verifies rejection or the absence of the prohibited effect:

| Test                                                     | Expected                                                         | Rule                                                | Mock server                                       |
| -------------------------------------------------------- | ---------------------------------------------------------------- | --------------------------------------------------- | ------------------------------------------------- |
| Synchronise without `payments.lookup`                    | `capability-not-supported`, no stored state presented as re-read | [capabilities 5.3](/en/docs/spec/capabilities#5.3)     | statement-only test provider (9.3.5), `PENDING_FOREVER` |
| Synchronise a terminal payment without `payments.lookup` | payment unchanged, `200`                                         | [capabilities 5.3.1](/en/docs/spec/capabilities#5.3.1) | statement-only test provider (9.3.5), `SUCCESS`   |
| Operation of a capability not advertised                 | `capability-not-supported`                                       | [capabilities 4.4](/en/docs/spec/capabilities#4.4)     | base test provider (9.3.5), `SUCCESS`             |
| Statements of a provider without `payments.statement`    | an empty collection                                              | [lifecycle 10.3.6](/en/docs/spec/lifecycle#10.3.6)     | base test provider (9.3.5)                        |
| `POST` without `Idempotency-Key`                         | `idempotency-key-required`                                       | [idempotency 1.3](/en/docs/spec/idempotency#1.3)       | none                                              |
| `callback_url` over `http` outside loopback              | creation rejected                                                | [API 5.1.8](/en/docs/spec/payments-api#5.1.8)          | `mock_openfsp`                                    |
| API request trying to set the state of a payment         | state unchanged                                                  | [lifecycle 6.1](/en/docs/spec/lifecycle#6.1)           | `mock_openfsp`, `PENDING_FOREVER`                 |
| Unknown, revoked, other-environment key                  | three indistinguishable `unauthenticated`                        | [authentication 4.7](/en/docs/spec/authentication#4.7) | none; assisted (4.7)                              |

**5.5.** Each outcome-dependent test identifies the mock-server scenario producing that outcome (4.9.3).

**5.6.** Client tests cover key reuse ([idempotency 7.1](/en/docs/spec/idempotency#7.1)), no retry after a non-retryable `4xx` ([idempotency 7.2](/en/docs/spec/idempotency#7.2)), recovery by reference ([API 5.2.3](/en/docs/spec/payments-api#5.2.3)), the non-authoritative return URL ([API 7.3](/en/docs/spec/payments-api#7.3)), tolerance of unknown members and persistent `pending` state. Subscriber tests cover verification before action ([webhooks 5.9](/en/docs/spec/webhooks#5.9)) and functional polling when all events are withheld ([webhooks 10.2](/en/docs/spec/webhooks#10.2)).

**5.7.** The suite MUST associate at least one test with each observable requirement. The report MUST state the mapping between tests and requirements.

**5.8. Payment outcomes.** Each test uses a scenario defined in 4.9.3:

| Test                                    | Expected                                                                                                                          | Rule                                                                                         | Mock server                                                           |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| Provider refusal                        | synchronisation `200`, `failed`, `failure_reason` `declined`, `failure_detail` carrying the provider's code and message unaltered | [lifecycle 7.2, 7.4](/en/docs/spec/lifecycle#7.4), [API 10.2.2](/en/docs/spec/payments-api#10.2.2) | `mock_openfsp`, `DECLINE`                                             |
| Insufficient funds                      | synchronisation `200`, `failed`, `failure_reason` `insufficient_funds`                                                            | [lifecycle 7.2](/en/docs/spec/lifecycle#7.2)                                                    | `mock_openfsp`, `INSUFFICIENT`                                        |
| Expiry reached at the provider          | `expired` after synchronisation, `completed_at` present                                                                           | [lifecycle 4, 5.3](/en/docs/spec/lifecycle#5.3) (a)                                             | `mock_openfsp`, `EXPIRE`, synchronisation after the one-minute expiry |
| Outcome without event, provider with lookup | state reported by the lookup, after synchronisation                                                                           | [capabilities 5.2](/en/docs/spec/capabilities#5.2)                                              | `mock_openfsp`, `NO_CALLBACK`                                         |
| Provider error at creation              | `502 provider-error`, `retryable` `true`, `effect` `unknown`; resend with same key without `Idempotent-Replay`                    | [API 10.6.5, 10.8.6](/en/docs/spec/payments-api#10.8.6)                                         | `mock_openfsp`, `PROVIDER_ERROR`                                      |

**5.9. Statements.** The following tests correspond to [lifecycle 10.4.1](/en/docs/spec/lifecycle#10.4.1):

| Test | Expected | Rule | Mock server |
| --- | --- | --- | --- |
| Successful payment | an entry whose `payment` equals the payment `id`, in the statement of its business day | [lifecycle 10.2.1](/en/docs/spec/lifecycle#10.2.1) | `mock_openfsp`, `SUCCESS` |
| Unsuccessful payment | no entry for that payment | [lifecycle 10.2.3](/en/docs/spec/lifecycle#10.2.3) | `mock_openfsp`, `DECLINE` |
| Range | only the entries of the days of the range, both ends included | [lifecycle 10.3.2](/en/docs/spec/lifecycle#10.3.2) | `mock_openfsp`, `SUCCESS` |
| Request without a period | `400 missing-field` | [lifecycle 10.3.2](/en/docs/spec/lifecycle#10.3.2) | `mock_openfsp` |
| Range of more than 31 days | `422 invalid-field` | [lifecycle 10.3.3](/en/docs/spec/lifecycle#10.3.3) | `mock_openfsp` |

**5.10. Capabilities.** Capability declaration, limit and delivery tests are defined below:

| Test                                                                                             | Expected                                                                     | Rule                                                 | Mock server                                                |
| ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------- |
| Capabilities advertised for each simulated provider                                              | no reserved or withdrawn name                                                | [capabilities 2.2, 7.2](/en/docs/spec/capabilities#7.2) | `mock_openfsp` and the test providers (9.3.5)              |
| Amount equal to `min_amount`, then to `max_amount`                                               | payment created (`201`)                                                      | [capabilities 6.7, 7.3](/en/docs/spec/capabilities#7.3) | `mock_openfsp`, `SUCCESS`; limits declared, assisted (4.7) |
| Amount one cent below `min_amount`, one cent above `max_amount`, not a multiple of `amount_step` | `amount-out-of-range` carrying the declared limits; no payment created       | [capabilities 6.7, 7.3](/en/docs/spec/capabilities#7.3) | `mock_openfsp`, `SUCCESS`; limits declared, assisted (4.7) |
| Event delivered to `callback_url`                                                                | `payment.succeeded` signed, verified with `webhook_keys`                     | [API 5.1.8](/en/docs/spec/payments-api#5.1.8)           | `mock_openfsp`, `SUCCESS`                                  |

**5.11. Authentication.** Authentication failure cases are assessed according to the following table:

| Test                                                                 | Expected                                                                                                               | Rule                                                          | Mock server          |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- | -------------------- |
| Missing, malformed, unknown, revoked, expired, other-environment key | six `unauthenticated` with the same `title`, no distinguishing `detail`; `WWW-Authenticate: Bearer` on the missing key | [authentication 3.3, 4.7, 7.6](/en/docs/spec/authentication#7.6) | none; assisted (4.7) |

**5.12.** Tests in 5.9 belong to the `payments.statement` profile. The `callback_url` delivery test in 5.10 belongs to `webhooks.per_payment_url`. A profile’s tests do not apply to a server that does not declare the corresponding capability.

## 6. Versions

**6.1.** A suite version assesses one minor protocol version and MUST reject any unknown major version.

**6.2.** The result identifies the suite version, protocol version, target, level, profiles, date and configuration.

**6.3.** A result applies only to the assessed configuration. A result obtained against the mock server does not characterise a real service (9.8).

**6.4.** A result becomes outdated when the implementation or protocol version changes. Any party citing it MUST specify the assessed implementation version.

**6.5.** A patch release MAY add tests; the suite’s release notes MUST identify those additions.

## 7. Report

**7.1.** The report is machine-readable. The specification defines its content without prescribing its presentation.

**7.2.** The report contains the triple in 1.1, suite version, date and configuration, together with the result and corresponding requirement for each test.

**7.3.** For a failed test, the result states the expected and observed behaviour.

**7.4.** On every execution, including a successful one, the report MUST state the suite’s limitations (8.1).

**7.5.** The party publishing a report SHOULD provide the configuration required to reproduce it.

**7.6.** Claims based on a report are governed by [governance 8](https://github.com/openfspht/governance/blob/main/GOVERNANCE.md#8-name-and-conformance-marks).

## 8. Security

**8.1.** A conformance report does not constitute a security audit (7.4).

**8.2.** The suite MUST NOT require production credentials. It runs against a test environment or the mock server (9).

## 9. Mock server

The requirements of section 9 apply to the reference mock server.

### 9.1. Role

**9.1.1.** The mock server implements the API for fictitious payment services. It supports assessment of clients and the suite without access to a real service.

**9.1.2.** It supports testing of the client and suite within the limits defined in 9.8.

**9.1.3.** Only capabilities with a specification are simulated ([capabilities 2.2](/en/docs/spec/capabilities#2.2)).

### 9.2. Guiding rule

**9.2.1.** The simulator introduces no additional capability. Every optional capability is absent from at least one simulated provider, including the test providers in 9.3.5.

### 9.3. Simulated providers

**9.3.1.** The reference simulated implementation is described below:

| Provider       | Capabilities                                                                    | Case exercised                                                           |
| -------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `mock_openfsp` | `payments`, `payments.lookup`, `payments.statement`, `webhooks.per_payment_url` | Reference server (9.3.2): lookup, statement, events to `callback_url`.   |

**9.3.2.** The `mock_openfsp` service exposes the API directly and signs deliveries under [webhooks](/en/docs/spec/webhooks), based on RFC 9421.

**9.3.3.** Proximity payment support is deferred to a later version. No simulated provider declares the corresponding capabilities.

**9.3.4.** Simulated identifiers use the `mock_` prefix reserved in the [registry](/en/docs/registry). No real service receives an identifier in that namespace.

**9.3.5.** The server also exposes test-only simulated providers defined by capability flags. They isolate cases that `mock_openfsp` does not distinguish:

| Test provider  | Capabilities                     | Case exercised                                                                                  |
| -------------- | -------------------------------- | ----------------------------------------------------------------------------------------------- |
| Base           | `payments`                       | Operation of a capability not advertised; statements of a provider without `payments.statement`. |
| Statement only | `payments`, `payments.statement` | Synchronisation without `payments.lookup`.                                                      |

**9.3.6.** The `mock_openfsp` service delivers only terminal-transition events to `callback_url` ([API 5.1.8](/en/docs/spec/payments-api#5.1.8)), without delivering `payment.created`. The per-payment `sequence` includes the undelivered creation, so the transition carries `2` ([webhooks 8.1](/en/docs/spec/webhooks#8.1)).

**9.3.7.** In addition to its active key, `mock_openfsp` publishes a revoked key, an expired key and a second principal’s key. These keys allow tests in 5.3 and 5.11 to run without operator intervention.

### 9.4. Failures

**9.4.1.** The mock server produces every scenario of 4.9.3.

**9.4.2.** Outside automatic mode (9.4.4), a payment without a declared scenario uses `SUCCESS`.

**9.4.3.** Mock-server responses occur after a brief, fixed delay and are never instantaneous.

**9.4.4.** In automatic mode, the control interface assigns each new payment the next scenario in a rotation of those available for its provider.

### 9.5. Control

**9.5.1.** The mock server provides the control interface of 4.9. It does not allow the clock to be changed; expirations are assessed with `EXPIRE` (4.9.3).

**9.5.2.** The test suite controls this interface. The assessed server never controls it.

**9.5.3.** The interface is bound to loopback or protected by the test environment’s authentication.

### 9.6. Determinism

**9.6.1.** On a freshly started instance, a given sequence of requests always produces the same sequence of responses.

**9.6.2.** State belongs to the instance and is not retained after restart.

### 9.7. Separation from production

**9.7.1.** Each simulated payment carries a `mock_` identifier under 9.3.4.

**9.7.2.** The mock server never returns a real provider identifier and produces no artefact that could be interpreted as settlement.

### 9.8. Limitations

**9.8.1.** The mock server cannot establish that a real service follows its documentation.

**9.8.2.** The mock server provides no load-capacity measurement.

**9.8.3.** Scenarios are constructed from the specification’s rules.
