---
title: Capabilities and limits
description: How a gateway announces what each provider supports, how a client discovers it, and how amount limits are declared and enforced.
---

I explain these choices in [Decisions](/docs/decisions#0005).

## 1. Capability

**1.1.** A capability is a named feature, supported or not for a given provider.

**1.2.** Capabilities are reported per provider, never for the gateway as a whole.

**1.3.** A gateway MUST announce a capability only if the provider performs the operation itself. It MUST NOT announce a capability obtained by emulation,
approximation or composition of other operations.

**1.4.** Capability `payments`: [API 2.1](/docs/spec/payments-api#2.1).

## 2. Names and registry

**2.1.** A capability name matches `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$`: domain, then operation.

**2.2.** Registry. A _reserved_ name has no specification yet and MUST NOT be announced.

| Name                           | Status              | Meaning                                                                                                                                                                             |
| ------------------------------ | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `payments`                     | specified, required | Create, read, sync a payment ([API](/docs/spec/payments-api)).                                                                                                                      |
| `payments.lookup`              | specified           | Authoritative lookup of the state at the provider (5).                                                                                                                              |
| `payments.statement`           | specified           | Transaction statement over an authenticated channel ([lifecycle 6.7](/docs/spec/lifecycle#6.7)), readable by the client ([statements](/docs/spec/lifecycle#10)).                    |
| `payments.fee`                 | specified           | The provider reports fees ([data model 8](/docs/spec/data-model#8)).                                                                                                                |
| `payments.refund`              | reserved            | Refund of a captured payment.                                                                                                                                                       |
| `payments.capture`             | reserved            | Separate authorization and capture.                                                                                                                                                 |
| `payments.cancel`              | reserved            | Cancellation before completion.                                                                                                                                                     |
| `payments.proximity_cpm`       | reserved            | Native resolution of tokens presented by the payer.                                                                                                                                 |
| `confirmation_requests`        | reserved            | Timed confirmation by the payer.                                                                                                                                                    |
| `confirmation_requests.cancel` | reserved            | Withdrawal of a request before the payer answers.                                                                                                                                   |
| `transfers`                    | reserved            | Sending funds to a beneficiary.                                                                                                                                                     |
| `webhooks.emit`                | specified           | Signed events to the client ([webhooks](/docs/spec/webhooks)).                                                                                                                      |
| `webhooks.verify`              | specified           | Callbacks signed by the provider ([lifecycle 6.5](/docs/spec/lifecycle#6.5) a).                                                                                                     |
| `webhooks.per_payment_url`     | specified           | Callback URL specific to each payment ([lifecycle 6.6](/docs/spec/lifecycle#6.6)), passed to a native provider through `callback_url` ([API 5.1.8](/docs/spec/payments-api#5.1.8)). |

**2.3.** Adding a name requires a decision record. An addition is not a breaking change (4.3).

**2.4.** A gateway MAY announce names outside the registry, prefixed with a reversed DNS name it controls (`com.example.payments.instalments`), and MUST NOT
invent unprefixed names.

**2.5.** Capabilities are not versioned: a change of meaning requires a new name.

**2.6.** The gateway MUST use the registered identifier of each provider
([registry](/docs/registry)).

**2.7.** A provider identifier is registered by pull request on the registry, without a decision record.

**2.8.** Identifiers are permanent. A renamed provider receives a new identifier and the old one is marked superseded.

## 3. Discovery

### 3.1. Configuration document

```
GET /.well-known/openfsp-configuration
```

Unauthenticated (RFC 8615). The shape follows OpenID Connect discovery: absolute URLs suffixed `_endpoint` or `_uri`, and lists suffixed `_supported`.

```json
{
  "issuer": "https://gateway.example",
  "protocol_version": "0.1.0",
  "api_base": "https://gateway.example/v1",
  "payments_endpoint": "https://gateway.example/v1/payments",
  "capabilities_endpoint": "https://gateway.example/v1/capabilities",
  "statements_endpoint": "https://gateway.example/v1/statements",
  "statement_entries_endpoint": "https://gateway.example/v1/statement_entries",
  "gateway_statements_endpoint": "https://gateway.example/v1/gateway_statements",
  "webhook_keys": [
    { "kid": "whk_06GWCT5DMSTMH111XG1Q28R4MW", "kty": "OKP", "crv": "Ed25519", "alg": "EdDSA", "use": "sig", "x": "…", "openfsp_status": "active" }
  ],
  "authentication_methods_supported": ["bearer"],
  "scopes_supported": ["capabilities:read", "payments:read", "payments:write", "statements:read"],
  "capabilities_supported": ["payments", "payments.lookup", "payments.statement", "webhooks.emit", "webhooks.per_payment_url", "webhooks.verify"],
  "webhook_signature_algorithms_supported": ["ed25519"]
}
```

**3.1.1.** The document MUST NOT reveal the providers in use, any information about the merchant, the version of the gateway software, or the administration
interface.

**3.1.2.** `protocol_version` is the targeted specification version. A client MUST NOT infer any capability from it.

**3.1.3.** `issuer` is the public URL of the gateway, without a trailing slash. A client SHOULD read endpoints from this document rather than build them.

**3.1.4.** `capabilities_supported` lists the capability names (2) the gateway software can serve. This list MUST NOT depend on the configured providers. What
a provider actually announces is read from `/v1/capabilities` (3.2).

**3.1.5.** `webhook_keys` holds the public webhook signing keys ([webhooks 6.1](/docs/spec/webhooks#6.1)). This is their only publication point.

### 3.2. Capabilities

```
GET /v1/capabilities
```

Authenticated.

```json
{
  "protocol_version": "0.1.0",
  "providers": [
    {
      "id": "moncash",
      "display_name": "MonCash",
      "capabilities": ["payments", "payments.lookup"],
      "payments": {
        "next_actions": ["redirect"],
        "payer_required": false,
        "return_url_required": true,
        "expiry_guaranteed": false,
        "locales": []
      }
    }
  ]
}
```

**3.2.1.** Provider fields:

| Field          | Type             | Presence | Notes                                                        |
| -------------- | ---------------- | -------- | ------------------------------------------------------------ |
| `id`           | string           | REQUIRED | Registered identifier. Equal to the `provider` of a payment. |
| `display_name` | string           | REQUIRED | For display, not an identifier.                              |
| `logo_url`     | string           | OPTIONAL | Absolute URL of a logo to display next to `display_name`.    |
| `capabilities` | array of strings | REQUIRED | Always contains `payments`.                                  |
| `payments`     | object           | REQUIRED | 3.2.2.                                                       |

**3.2.2.** `payments` object:

| Field                 | Type             | Meaning                                                                              |
| --------------------- | ---------------- | ------------------------------------------------------------------------------------ |
| `next_actions`        | array of strings | `next_action` types produced ([API 4.2](/docs/spec/payments-api#4.2)).               |
| `payer_required`      | boolean          | `payer` required at creation.                                                        |
| `return_url_required` | boolean          | `return_url` required at creation.                                                   |
| `expiry_guaranteed`   | boolean          | Guarantee of [lifecycle 5.3](/docs/spec/lifecycle#5.3) c.                            |
| `limits`              | object           | OPTIONAL. Amount limits (6.4).                                                       |
| `locales`             | array of strings | `locale` values passed to the provider ([API 5.1.7](/docs/spec/payments-api#5.1.7)). |

**3.2.3.** `expiry_guaranteed` MUST be `false` unless the condition of [lifecycle 5.3](/docs/spec/lifecycle#5.3) (c) is met.

**3.2.4.** The response SHOULD carry `Cache-Control` with a `max-age` of at most one hour.

**3.2.5.** As an exception to 1.3, `webhooks.emit` appears in the list of every provider for which the gateway emits events.

**3.2.6.** A native provider announces a single provider: itself, under its registered identifier (2.6).

## 4. Obligations

**4.1.** A client MUST NOT invoke an operation whose capability is not announced for the chosen provider.

**4.2.** A client MUST handle `capability-not-supported` at any time, and SHOULD then read the capabilities again.

**4.3.** A client MUST ignore an unknown capability name.

**4.4.** The gateway MUST reject with `capability-not-supported` any operation whose capability it does not announce, even if it can perform it.

**4.5.** The gateway MAY detect that a provider has suspended a capability. If it detects it, it MUST NOT announce it.

## 5. `payments.lookup`

**5.1.** `payments.lookup` announces an authoritative lookup of the current state at the provider.

**5.2.** If it is announced, sync ([API 5.3](/docs/spec/payments-api#5.3)) MUST read the state at the provider.

**5.3.** Otherwise, sync MUST return `capability-not-supported` and MUST NOT return the stored state as if it had been read again.

**5.3.1.** Exception: a terminal payment is returned unchanged with `200` ([API 5.3.3](/docs/spec/payments-api#5.3.3)).

**5.4.** Without `payments.lookup`, reconciliation relies on the other sources of [lifecycle 6.5](/docs/spec/lifecycle#6.5).

## 6. Amount limits

**6.1.** A provider's limits are the minimum and maximum amount of a transaction on the merchant account, set by the provider for that merchant.

**6.2.** The operator declares the limits per provider, in the gateway configuration. No administration endpoint is required.

**6.3.** The gateway MUST NOT invent a limit, nor infer one from past failures.

**6.4.** A provider's `payments` object (3.2.2) carries an OPTIONAL `limits` member:

```json
"limits": {
  "min_amount": { "amount": 1000, "currency": "HTG" },
  "max_amount": { "amount": 7500000, "currency": "HTG" },
  "amount_step": { "amount": 100, "currency": "HTG" }
}
```

| Field         | Type    | Presence | Notes                                                      |
| ------------- | ------- | -------- | ---------------------------------------------------------- |
| `min_amount`  | `Money` | OPTIONAL | 6.5.                                                       |
| `max_amount`  | `Money` | OPTIONAL | 6.5.                                                       |
| `amount_step` | `Money` | OPTIONAL | The amount MUST be a multiple of it. `100`: whole gourdes. |

**6.5.** A missing limit means "unknown", not "unlimited". A client MUST NOT display it as the absence of a cap.

**6.6.** If `min_amount` and `max_amount` are both present, `min_amount` MUST be less than or equal to `max_amount`.

**6.7.** At creation ([API 5.1](/docs/spec/payments-api#5.1)), the gateway MUST reject an amount below `min_amount`, above `max_amount` or not a multiple of
`amount_step`, with `amount-out-of-range`, before any call to the provider. The response carries the limits as extension members:

```json
{
  "type": "https://openfsp.org/problems/amount-out-of-range",
  "title": "Amount out of range",
  "status": 422,
  "retryable": false,
  "effect": "none",
  "request_id": "req_01J9ZR2T4V6X8Z0B2D4F6H8K0M",
  "min_amount": { "amount": 1000, "currency": "HTG" },
  "max_amount": { "amount": 7500000, "currency": "HTG" },
  "amount_step": { "amount": 100, "currency": "HTG" }
}
```

**6.7.1.** An amount that [data model 3.6](/docs/spec/data-model#3.6) rejects (zero or negative) is rejected with `invalid-field` before the limit check, even
if limits are declared.

**6.8.** `amount-out-of-range` is an error caused by the request: its response is stored under [idempotency 5.1](/docs/spec/idempotency#5.1). After a change of
limits, a client that submits the creation again MUST use a new `Idempotency-Key`.

**6.9.** A payment refused by the provider because of a payer cap, or of a limit the gateway did not know, becomes `failed` with `limit_exceeded`
([lifecycle 7.2](/docs/spec/lifecycle#7.2)). The gateway MUST NOT convert it into `amount-out-of-range`.

## 7. Conformance

**7.1.** A conformant gateway MUST serve both endpoints of 3.

**7.2.** The conformance suite checks 2.2.

**7.3.** The suite tests 6.7 at both limits (limit accepted, limit exceeded by one cent) and checks that no call reaches the simulated provider.

## 8. Security

**8.1.** The configuration document SHOULD be rate-limited.

**8.2.** Announcing a capability grants no authorization: the gateway MUST check the key's scope independently
([authentication 6](/docs/spec/authentication#6)).

**8.3.** Limits are served only by the authenticated endpoint of 3.2, never by the configuration document (3.1.1).
