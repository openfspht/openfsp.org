---
title: Idempotency
description: "Request keys, replay and indeterminate outcomes: idempotency rules for the payment contract."
---

I require a stable request key so a lost response does not cause a second payment. Recovery after an unknown outcome follows [decision 0004](/docs/decisions#0004).

## 1. Covered operations

**1.1.** Every `POST`, `PATCH` or `DELETE` on the client API is subject to idempotency, unless exempted (1.4). Endpoints outside the client API are not covered.

**1.2.** `GET` and `HEAD` are not covered. A client MAY resend them freely.

**1.3.** A client MUST send `Idempotency-Key` on every covered operation. The server MUST reject such a request without the header, without executing it,
with `idempotency-key-required`.

**1.4.** A decision record MAY exempt a named operation when both hold: running it twice has no effect, and a stored response served in its place would report a
state older than the execution. For an exempted operation, the server MUST NOT require the key, MUST NOT store a response, and MUST ignore the header if present.

## 2. Key

**2.1.** The value is an `IdempotencyKey`: 1 to 255 characters from `A-Za-z0-9_-`. The server MUST reject a request with a malformed key, without executing
it, with `invalid-field` ([API 10.8.1](/docs/spec/payments-api#10.8.1)) and no `errors`: `field` only points into the body
([API 10.7.1](/docs/spec/payments-api#10.7.1)).

**2.2.** A client SHOULD generate the key as a UUID (RFC 9562) or from at least 128 bits of cryptographic randomness, and SHOULD NOT derive it from business data.

**2.3.** A record is identified by the triple (principal, operation, key). The server MUST NOT serve a stored response to a principal other than the one that
created it.

## 3. Processing

_P_ is the principal, _O_ the operation, _K_ the key and _F_ the fingerprint from 4.

**3.1. First request.** With no record for (_P_, _O_, _K_), the server runs the operation, then, once the outcome is settled (5), stores _F_, the status and
the response body.

**3.2. Replay.** If the record exists with the same fingerprint, the server MUST NOT run the operation. It MUST return the stored status and body, byte for
byte, with `Idempotent-Replay: true`.

**3.3. Conflict.** If the fingerprint differs, the server MUST reject the request without running it, with `idempotency-key-reused` (`422`).

**3.4. In progress.** If the first request has no settled outcome yet, the server MUST NOT run the second one in parallel. It MUST either hold it or reject it
with `idempotency-request-in-progress` (`409`) and `Retry-After`.

**3.5.** Creating the record and running the operation MUST be mutually exclusive (conditional insert, lock or equivalent). A read-then-write check MUST NOT be
used.

## 4. Fingerprint

**4.1.** _F_ is the SHA-256 digest of the parsed JSON body with object members sorted. Amounts are integers: a floating-point number is rejected before the
fingerprint is computed. An empty body has the fingerprint of `{}`.

**4.2.** Only the body goes into the fingerprint. Path, query parameters and headers are excluded.

## 5. Storage

**5.1.** The server MUST store the response only once the outcome is settled:

- a success, including a `failed` payment;
- an error caused by the request itself: validation, unknown field, `reference-conflict`.

**5.2.** The server MUST NOT store:

- an internal error whose effect is unknown;
- a timeout or failure of a system the operation depends on, whose effect is unknown;
- a stop before the outcome is persisted;
- an `idempotency-request-in-progress` response.

**5.3.** The server MUST NOT modify a stored response.

## 6. Retention and reference

**6.1.** The server MUST keep records for at least 24 hours, SHOULD keep them for 7 days, and MUST publish its retention period.

**6.2.** After that period, the same key is treated as a first request. The server MUST enforce `reference` uniqueness independently of idempotency records.

**6.3.** Payment creation:

| Key               | Body      | Reference | Result                         |
| ----------------- | --------- | --------- | ------------------------------ |
| same, not expired | same      | same      | replay (3.2)                   |
| same              | different | any       | `idempotency-key-reused` (3.3) |
| expired           | same      | same      | `reference-conflict`           |
| different         | any       | same      | `reference-conflict`           |
| different         | any       | different | new payment                    |

## 7. Client

**7.1.** A client MUST use one key per logical operation and the same key for every resend of that operation.

**7.2.** A client MUST NOT resend a request that received a `4xx`, except `idempotency-request-in-progress` and `rate-limited`.

**7.3.** After resends, a client MUST read the resource to learn the outcome, and MUST NOT infer it from the last response received.

**7.4.** A client MUST space its resends and honour `Retry-After`. It SHOULD use exponential backoff with jitter.

**7.5.** A client SHOULD persist the key before sending the request.

## 8. Security

**8.1.** The key alone MUST NOT be used as a lookup identifier: records are scoped per principal (2.3). The key is not a secret and MUST NOT grant any
authorization.

**8.2.** The server MUST rate-limit creation per principal and SHOULD cap the number of records per principal, rejecting excess requests rather than deleting
records.

**8.3.** Stored responses MAY contain personal data and MUST be protected like the resources they come from.
