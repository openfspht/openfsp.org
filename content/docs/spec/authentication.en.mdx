---
title: Authentication
description: Bearer-key authentication, identities, authorisation and key lifecycle.
---

Clients are authenticated using bearer keys; scopes determine the permitted operations. [Decision 0007](/en/docs/decisions#0007) documents key management, storage and rotation.

## 1. Scheme

**1.1.** The client authenticates using an API key presented as a bearer token. All endpoints require authentication except the configuration document ([capabilities 3.1](/en/docs/spec/capabilities#3.1)), which publishes webhook keys ([webhooks 6.1](/en/docs/spec/webhooks#6.1)), the conformance preparation endpoint, protected where needed by the operator’s access code ([conformance 4.8.7](/en/docs/spec/conformance#4.8.7)), and a health check outside `/v1`.

**1.2.** The server MUST NOT permit unauthenticated access to other endpoints, including in development mode.

**1.3.** A deployment MAY additionally require mutual TLS, an address allowlist or an upstream authorisation server. These mechanisms MUST NOT replace the requirements in section 3.

## 2. Key format

**2.1.** The key follows the form `ofsp_<env>_<secret>`. The value of `<env>` is `live` or `test`; `<secret>` contains at least 34 characters from `A-Za-z0-9`, so the part not retained in cleartext under 4.4 represents at least 128 bits:

```
ofsp_live_7Kq2NfPzR4wYb9LdHt3XvA6mSjE0uCgBp8
```

**2.2.** The value of `<secret>` MUST be produced by a cryptographic generator and provide at least 128 bits of entropy. It MUST NOT be derived from predictable data.

**2.3.** The server is configured for a single environment and MUST reject keys belonging to another environment with `unauthenticated`.

**2.4.** The key is opaque: it MUST NOT encode a principal, scope or expiration date.

**2.5.** The server MAY increase the length of `<secret>` or add a checksum, provided 2.1 remains satisfied.

## 3. Presentation

**3.1.** The client MUST send the key in the `Authorization` header using the `Bearer` scheme (RFC 9110):

```
Authorization: Bearer ofsp_live_7Kq2NfPzR4wYb9LdHt3XvA6mSjE0uCgBp8
```

**3.2.** The server MUST NOT accept the key in a query parameter, body, cookie or another header.

**3.3.** If `Authorization` is absent, unreadable or uses a scheme other than `Bearer`, the server MUST return `unauthenticated` with `WWW-Authenticate: Bearer`.

**3.4.** The scheme name is case-insensitive; the key value is case-sensitive.

**3.5.** The server MUST reject any request containing multiple keys with `unauthenticated`.

## 4. Storage and comparison

**4.1.** The server MUST NOT retain a key in a reversible representation. It retains a digest of the key.

**4.2.** The digest MUST be computed over the complete key using SHA-256 or a stronger algorithm.

**4.3.** A slow password-hashing algorithm, such as Argon2id, scrypt or bcrypt, SHOULD NOT be used.

**4.4.** The server MAY retain and index a cleartext lookup prefix consisting of the first 12 characters of `<secret>`.

**4.5.** Comparison between the presented key’s digest and the stored digest MUST use constant time.

**4.6.** Processing an unknown key and a revoked key SHOULD take indistinguishable time. If the prefix matches no record, the server MUST nevertheless compute a digest and compare it with a dummy value in constant time. The two paths MUST NOT differ through a conditional operation specific to one case, such as case-specific logging.

**4.7.** Absent, malformed, unknown, revoked, expired and wrong-environment keys MUST all produce `unauthenticated` with the same `title` and no `detail` that distinguishes the cause.

**4.8.** At every logging level, the server MUST NOT record a presented key beyond its lookup prefix. Failures are recorded with that prefix and `request_id`. The `Authorization` header and fields containing API keys MUST be redacted before the log line is constructed.

## 5. Principal

**5.1.** The principal is the identity established by successful authentication, denoted _P_ in [idempotency 2.3](/en/docs/spec/idempotency#2.3).

**5.2.** Each key belongs to exactly one principal. A principal MAY hold multiple keys.

**5.3.** A principal’s keys share its resources and idempotency records. The server MUST NOT isolate by key where the specification defines isolation by principal.

**5.4.** The principal has an opaque, stable identifier ([data model 6.1](/en/docs/spec/data-model#6.1)). This identifier appears in logs and audit records but is never exposed through the API.

**5.5.** Each principal belongs to a merchant account. Principals in that account access the same resources. Scopes restrict permitted operations and do not partition resources between principals.

**5.6.** A principal MUST NOT read or act on a resource belonging to another merchant account. The server returns `not-found` as though the resource did not exist.

## 6. Scopes

**6.1.** Each key is associated with a set of scopes.

**6.2.** Available scopes are defined by the following registry:

| Scope               | Permits                                                                                                           |
| ------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `capabilities:read` | Capability discovery ([capabilities 3.2](/en/docs/spec/capabilities#3.2)).                                           |
| `payments:read`     | Read a payment, look up by reference ([API 5.2](/en/docs/spec/payments-api#5.2)).                                    |
| `payments:write`    | Create a payment ([API 5.1](/en/docs/spec/payments-api#5.1)).                                                         |
| `statements:read`   | Read statements ([lifecycle 10.3](/en/docs/spec/lifecycle#10.3)).                                  |

**6.3.** Granting a scope does not imply granting any other scope.

**6.4.** If the required scope is absent, the server MUST return `forbidden`, not `unauthenticated` or `not-found`, whether or not the resource exists, so as not to disclose its existence.

**6.5.** Every key includes `capabilities:read`. The server adds this scope at issuance and MUST NOT allow its removal. The client can therefore discover available operations before calling them.

**6.6.** Adding a scope requires a decision record alongside the corresponding operation.

**6.7.** A key limited to `capabilities:read` authorises discovery only. The server MUST NOT treat it as unrestricted.

**6.8.** Issuance tools SHOULD default to scopes following the principle of least privilege.

## 7. Rotation, revocation, expiry

**7.1.** The server MUST allow multiple keys of the same principal to be valid simultaneously.

**7.2.** Rotation consists of issuing a new key, deploying it, verifying its use and then revoking the previous key. Issuance MUST NOT invalidate the principal’s other keys.

**7.3.** The server MUST NOT accept a revoked key or retain a cached authentication decision for more than 60 seconds after revocation. The cache MUST be invalidated on revocation.

**7.4.** A revoked key MUST NOT be reactivated and its secret cannot be reissued.

**7.5.** A revoked key’s record MUST be retained for audit without the secret.

**7.6.** A key MAY have an expiry time. After expiry, it MUST be rejected with `unauthenticated`. The operator SHOULD be informed before that time.

**7.7.** The secret MUST be displayed exactly once, at issuance, with no possibility of later display.

**7.8.** The server SHOULD retain and display each key’s last-use date.

## 8. Interplay

**8.1.** Idempotency records remain valid after API key rotation (5.3). They never become accessible to another principal ([idempotency 2.3](/en/docs/spec/idempotency#2.3)).

**8.2.** Rate limiting is defined per principal rather than per key.

**8.3.** The errors `unauthenticated` and `forbidden` are defined in [API 10.8.2](/en/docs/spec/payments-api#10.8.2).

**8.4.** The server MUST NOT send an API key to a webhook endpoint. The subscriber MUST NOT authenticate delivery through any mechanism other than its signature ([webhooks 5](/en/docs/spec/webhooks#5)).

## 9. Audit

**9.1.** For every authenticated request, the server MUST record the principal, lookup prefix, operation, `request_id` and result.

**9.2.** Authentication failures MUST be recorded with the same fields except the principal.

**9.3.** Every key issuance or revocation MUST be recorded with its time and scopes.

**9.4.** These records MUST NOT include any key secret.

## 10. Conformance

**10.1.** A conforming server applies the requirements for presentation in section 3, storage and comparison in section 4, principals in section 5, scopes in section 6, and rotation and revocation in section 7.

**10.2.** The suite verifies 4.7 with an unknown key, a revoked key and a wrong-environment key. The three responses are indistinguishable.

**10.3.** Authentication is a general specification requirement and is not declared as a capability.

## 11. Security

**11.1.** The server SHOULD rate-limit failed authentication attempts per source.
