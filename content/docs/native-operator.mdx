---
title: Implémenter OpenFSP
description: Points d’attention d’une implémentation native de l’API OpenFSP et exécution de la suite de conformité.
---

Une implémentation native expose l’API OpenFSP dans le système du fournisseur de services de paiement. Les exigences sont celles de la [spécification](/docs/spec) ; cette page indique les points d’attention et la façon d’exécuter la suite.

## Surface HTTP

| Surface                                                   | Rôle                                                                                        | Point d'attention pour la cible native                                                                                                    |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `/.well-known/openfsp-configuration`                      | Découverte publique de l'émetteur, des points d'accès, des méthodes et des clés de webhook. | Lisez la [structure de configuration](/docs/spec/capabilities#3.1) et les [clés de signature](/docs/spec/webhooks#6.1).           |
| `GET /v1/capabilities`                                    | Capacités et limites effectivement exposées.                                                | Annoncez chaque fournisseur servi sous son identifiant enregistré ([2.6](/docs/spec/capabilities#2.6)).     |
| `POST /v1/payments`                                       | Création selon le contrat, avec clé d'idempotence.                                          | Respecter le format, les refus, les rejeux et les effets inconnus ; ne pas traiter une création sans réponse comme un échec certain. |
| `GET /v1/payments/{id}` et `GET /v1/payments?reference=…` | Lecture du paiement et récupération après perte d'une réponse.                              | Le marchand connaît sa référence avant l'appel ; il ne doit pas avoir besoin de reconstruire un identifiant opaque.                       |
| Relevés et notifications                                  | Fonctions conditionnées par les capacités correspondantes.                                  | Une fonction réservée ou non prise en charge ne doit pas être présentée comme disponible.                                                 |

Les clients utilisent les URL publiées dans le document de découverte ([capacités 3.1.3](/docs/spec/capabilities#3.1.3)). L’[identifiant `provider`](/docs/registry) désigne le service enregistré et reste distinct de son nom commercial affiché.

## Notifications

Lorsque la création porte `callback_url`, appliquez l’[API 5.1.8](/docs/spec/payments-api#5.1.8). La [conformité 5.4](/docs/spec/conformance#5.4) et la [conformité 5.10](/docs/spec/conformance#5.10) vérifient la livraison d’un `payment.succeeded` signé, la publication des clés et le rejet d’une URL `http` hors bouclage.

## Environnement de test

En environnement de test, l’implémentation fournit la préparation ([conformité 4.8](/docs/spec/conformance#4.8)), qui délivre la clé de test et les entrées du [4.8.4](/docs/spec/conformance#4.8.4), dont `bounded-provider`, et l’interface de contrôle ([conformité 4.9](/docs/spec/conformance#4.9)), par laquelle la suite choisit l’issue de chaque paiement. Sans l’interface de contrôle, les tests qui choisissent une issue échouent.

## Exécuter la suite

Contre le serveur simulé de référence `mock_openfsp` de la démonstration en ligne :

```bash
curl -fsSL https://cdn.openfsp.org/validate.sh | sh -s -- https://simulator-api.openfsp.org/mock_openfsp
```

Contre votre implémentation, son adresse suffit :

```bash
curl -fsSL https://cdn.openfsp.org/validate.sh | sh -s -- https://operator.example \
  --report conformance-report.json \
  --webhook-port 8098 \
  --webhook-url https://receiver.example/webhooks
```

Ce script exécute l’image du validateur, qui embarque la suite ; Docker est son seul prérequis. La commande Docker équivalente :

```bash
docker run --rm -it --user "$(id -u):$(id -g)" -p 8098:8098 -v "$PWD:/work" ghcr.io/openfspht/validator:0.5.0 validate https://operator.example \
  --report conformance-report.json \
  --webhook-port 8098 \
  --webhook-url https://receiver.example/webhooks
```

Ajoutez `--access-code` si la préparation exige le code d’accès de l’exploitant ([conformité 4.8.7](/docs/spec/conformance#4.8.7)). Sans `--webhook-port`, aucun récepteur ne démarre et les tests de livraison sont non concluants, avec leur raison. `--webhook-url` donne l’adresse HTTPS publique redirigée vers ce port ; à défaut, la suite annonce `http://127.0.0.1:8098/webhooks`, joignable seulement depuis une instance locale.

Les [sources de l’implémentation native simulée](https://github.com/openfspht/openfsp/tree/main/backend/simulator/infrastructure/src/main/kotlin/dialects/openfsp) documentent son comportement.

## Lire et publier le résultat

Le code de sortie ne suffit pas : l’évaluation repose sur les verdicts du rapport ([conformité 7](/docs/spec/conformance#7)). Un test dont une entrée manque est assisté ([conformité 4.7](/docs/spec/conformance#4.7)) et laisse Core incomplet.

Une déclaration de conformité publiée précise le périmètre évalué et s’accompagne du rapport, de la configuration expurgée des secrets et des versions utilisées. Une [attestation signée](/docs/verify) permet d’en vérifier l’origine et l’intégrité.
