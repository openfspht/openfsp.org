---
title: Implement OpenFSP
description: Points of attention for a native implementation of the OpenFSP API and running the conformance suite.
---

A native implementation exposes the OpenFSP API within the payment service provider’s system. The requirements are those of the [specification](/en/docs/spec); this page lists the points of attention and how to run the suite.

## HTTP surface

| Surface                                                    | Role                                                                 | Native-target consideration                                                                                                      |
| ---------------------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `/.well-known/openfsp-configuration`                       | Public discovery of the issuer, endpoints, methods and webhook keys. | Read the [configuration structure](/en/docs/spec/capabilities#3.1) and [signing keys](/en/docs/spec/webhooks#6.1).                   |
| `GET /v1/capabilities`                                     | Actual capabilities and limits.                                      | Announce each provider you serve under its registered identifier ([2.6](/en/docs/spec/capabilities#2.6)). |
| `POST /v1/payments`                                        | Contract-defined creation, with an idempotency key.                  | Follow formats, refusals, replay and unknown-effect rules; a creation without a response is not a certain failure.               |
| `GET /v1/payments/{id}` and `GET /v1/payments?reference=…` | Retrieve a payment and recover after a lost response.                | The merchant knows its reference before the call; it must not need to reconstruct an opaque identifier.                          |
| Statements and notifications                               | Functions conditional on corresponding capabilities.                 | A reserved or unsupported function must not be presented as available.                                                           |

Clients use the URLs published in the discovery document ([capabilities 3.1.3](/en/docs/spec/capabilities#3.1.3)). The [`provider` identifier](/en/docs/registry) identifies the registered service and remains distinct from its displayed commercial name.

## Notifications

When creation carries `callback_url`, apply [API 5.1.8](/en/docs/spec/payments-api#5.1.8). [Conformance 5.4](/en/docs/spec/conformance#5.4) and [conformance 5.10](/en/docs/spec/conformance#5.10) check delivery of a signed `payment.succeeded`, key publication and rejection of an `http` URL outside loopback.

## Test environment

In the test environment, the implementation provides preparation ([conformance 4.8](/en/docs/spec/conformance#4.8)), which issues the test key and the inputs of [4.8.4](/en/docs/spec/conformance#4.8.4), including `bounded-provider`, and the control interface ([conformance 4.9](/en/docs/spec/conformance#4.9)), through which the suite chooses the outcome of each payment. Without the control interface, the tests that choose an outcome fail.

## Run the suite

Against the reference mock server `mock_openfsp`, from the [openfsp](https://github.com/openfspht/openfsp) repository and with the [development prerequisites](/en/docs/quickstart#2):

```bash title="Terminal 1: simulated provider"
make simulator
```

```bash title="Terminal 2: suite"
make validate TARGET=http://127.0.0.1:8090/mock_openfsp
```

Against your implementation, its address is enough: `make validate TARGET=https://operator.example`. The Makefile opens the suite’s webhook receiver on port 8099 and writes the report to `backend/validator/infrastructure/build/conformance-report.json`. Without the Makefile:

```bash
curl -fsSL https://cdn.openfsp.org/validate.sh | sh -s -- https://operator.example \
  --report conformance-report.json \
  --webhook-port 8098 \
  --webhook-url https://receiver.example/webhooks
```

Without a clone of the repository, this script is enough; it runs the validator image, which bundles the suite, and Docker is its only requirement. The equivalent Docker command:

```bash
docker run --rm -it --user "$(id -u):$(id -g)" -p 8098:8098 -v "$PWD:/work" ghcr.io/openfspht/validator:0.5.0 validate https://operator.example \
  --report conformance-report.json \
  --webhook-port 8098 \
  --webhook-url https://receiver.example/webhooks
```

Add `--access-code` when preparation requires the operator’s access code ([conformance 4.8.7](/en/docs/spec/conformance#4.8.7)). Without `--webhook-port`, no receiver starts and the delivery tests are inconclusive, with their reason. `--webhook-url` gives the public HTTPS address forwarded to that port; otherwise the suite announces `http://127.0.0.1:8098/webhooks`, reachable only from a local instance.

The [simulated native implementation sources](https://github.com/openfspht/openfsp/tree/main/backend/simulator/infrastructure/src/main/kotlin/org/openfsp/simulator/dialects/openfsp) and [Makefile](https://github.com/openfspht/openfsp/blob/main/Makefile) document its behaviour and execution parameters, respectively.

## Read and publish the result

The exit code is not enough: the assessment rests on the report’s verdicts ([conformance 7](/en/docs/spec/conformance#7)). A test whose input is missing is assisted ([conformance 4.7](/en/docs/spec/conformance#4.7)) and leaves Core incomplete.

A published conformance claim identifies the assessed scope and comes with the report, the configuration with secrets removed and the versions used. A [signed attestation](/en/docs/verify) allows its origin and integrity to be verified.
