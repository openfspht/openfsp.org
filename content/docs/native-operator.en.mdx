---
title: Implement OpenFSP
description: Steps for implementing the OpenFSP API natively and assessing applicable conformance requirements.
---

A native implementation exposes the OpenFSP interface within the payment service provider’s system. Merchant applications can communicate directly with this interface over HTTP or through a client library. Each merchant retains its account, keys and agreement with the provider.

This guide organises implementation tasks and related checks. Applicable requirements are defined in the [specification](/en/docs/spec).

## Read the contract in order

| Step                      | Decision to make                                                                                          | Reference                                                                             |
| ------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Identify the layer        | Distinguish merchant integration, API translation and inter-provider settlement.                          | [Standard architecture](/en/docs/architecture) and [decision 0001](/en/docs/decisions#0001) |
| Represent a payment       | Integer amounts in gourde cents, opaque identifiers, merchant references, timestamps and terminal states. | [Data model](/en/docs/spec/data-model), [lifecycle](/en/docs/spec/lifecycle)                |
| Expose exchanges          | Creation, retrieval, synchronisation, errors and recovery after connection loss.                          | [Payments API](/en/docs/spec/payments-api), [idempotency](/en/docs/spec/idempotency)        |
| Announce actual functions | Discovery, optional capabilities and limits, without emulating missing functions.                         | [Capabilities](/en/docs/spec/capabilities)                                               |
| Authenticate and notify   | Keys, scopes, signing-key publication, event verification and delivery.                                   | [Authentication](/en/docs/spec/authentication), [webhooks](/en/docs/spec/webhooks)          |
| Check applicable scope    | Target `server`, Core and profiles matching announced capabilities.                                       | [Conformance 3](/en/docs/spec/conformance#3)                                             |

## Prepare the HTTP surface

| Surface                                                    | Role                                                                 | Native-target consideration                                                                                                      |
| ---------------------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `/.well-known/openfsp-configuration`                       | Public discovery of the issuer, endpoints, methods and webhook keys. | Read the [configuration structure](/en/docs/spec/capabilities#3.1) and [signing keys](/en/docs/spec/webhooks#6.1).                   |
| `GET /v1/capabilities`                                     | Actual capabilities and limits.                                      | Announce each provider you serve under its registered identifier ([2.6](/en/docs/spec/capabilities#2.6)). |
| `POST /v1/payments`                                        | Contract-defined creation, with an idempotency key.                  | Follow formats, refusals, replay and unknown-effect rules; a creation without a response is not a certain failure.               |
| `GET /v1/payments/{id}` and `GET /v1/payments?reference=…` | Retrieve a payment and recover after a lost response.                | The merchant knows its reference before the call; it must not need to reconstruct an opaque identifier.                          |
| `POST /v1/payments/{id}/synchronize`                       | Synchronise state according to the contract.                         | Read native-target requirements alongside lifecycle rules and announced capabilities.                                            |
| Statements and notifications                               | Functions conditional on corresponding capabilities.                 | A reserved or unsupported function must not be presented as available.                                                           |

The URLs shown correspond to endpoints defined by the specification. Client applications should use the URLs published in the discovery document ([3.1.3](/en/docs/spec/capabilities#3.1.3)). The [`provider` identifier](/en/docs/registry) identifies the registered service and remains distinct from its displayed commercial name.

## Handle payment notifications

When payment creation uses `callback_url`, apply the conditions in [API 5.1.8](/en/docs/spec/payments-api#5.1.8). Native conformance scenarios check the delivery of a signed `payment.succeeded` event, the publication of Ed25519 keys and the rejection of HTTP notification URLs outside the loopback exceptions.

The [webhook specification](/en/docs/spec/webhooks) defines events, signatures, handling of out-of-order arrival and deduplication. Simulator behaviour introduces no implicit extension. Associated checks are described in [conformance 5.4](/en/docs/spec/conformance#5.4) and [5.10](/en/docs/spec/conformance#5.10).

## Observe a simulated native implementation

The reference repository includes `mock_openfsp`, a fictitious payment service that exposes the OpenFSP API directly.

From the [openfsp](https://github.com/openfspht/openfsp) repository, after installing the [development prerequisites](/en/docs/quickstart#2), run the following commands in two separate terminals:

```bash title="Terminal 1: simulated provider"
make simulator
```

```bash title="Terminal 2: suite against the implementation"
make validate TARGET=http://127.0.0.1:8090/mock_openfsp
```

The suite is given the address of the implementation only. It asks the implementation for its test keys and its control interface ([conformance 4.8 and 4.9](/en/docs/spec/conformance#4.8.1)), which lets it choose the outcome of each payment. The report is saved to `backend/validator/infrastructure/build/conformance-report.json`. The Makefile starts the suite’s webhook receiver on port 8099.

The [simulated native implementation sources](https://github.com/openfspht/openfsp/tree/main/backend/simulator/infrastructure/src/main/kotlin/org/openfsp/simulator/dialects/openfsp) and [Makefile](https://github.com/openfspht/openfsp/blob/main/Makefile) document its behaviour and execution parameters, respectively.

## Test your implementation

Prepare a dedicated test instance, the required keys and the capabilities to assess. Then build the command-line interface from the reference repository:

```bash
cd backend
./gradlew :validator:infrastructure:bootJar
cd ..
```

If your implementation prepares its own runs ([conformance 4.8](/en/docs/spec/conformance#4.8.1)), its address is enough: `make validate TARGET=https://operator.example`. Otherwise, run the suite with your own keys. Replace `operator.example` and set the variables holding the keys of your test environment:

```bash
java -jar backend/validator/infrastructure/build/libs/app.jar validate \
  --target server \
  --base-url https://operator.example \
  --api-key "$OPENFSP_NATIVE_TEST_KEY" \
  --conformance conformance \
  --report conformance-report.json \
  --input "statements-key=$OPENFSP_STATEMENTS_KEY" \
  --input "restricted-key=$OPENFSP_SECOND_PRINCIPAL_KEY" \
  --input "revoked-key=$OPENFSP_REVOKED_KEY" \
  --input "expired-key=$OPENFSP_EXPIRED_KEY" \
  --webhook-port 8098 \
  --webhook-url https://receiver.example/webhooks
```

| Input            | Key                                                                   |
| ---------------- | --------------------------------------------------------------------- |
| `statements-key` | A key with the `statements:read` scope.                               |
| `restricted-key` | A key of another principal with `payments:read` and `payments:write`. |
| `revoked-key`    | A key you have revoked.                                               |
| `expired-key`    | A key past its expiry.                                                |

The command-line interface has no default receiver port. Without `--webhook-port`, no receiver starts and the signed `payment.succeeded` delivery scenario does not run. The `--webhook-url` option supplies the public HTTPS address, forwarded to that port, used by the assessed instance for notifications. Without it, the announced address is `http://127.0.0.1:8098/webhooks`, which is accessible only to a local instance.

Some scenarios require a decline, an expiry or a state transition to be provoked. In the test environment, the implementation provides the control interface ([conformance 4.9](/en/docs/spec/conformance#4.9.1)) through which the suite chooses these outcomes. Without it, these scenarios fail.

## Read and publish the result

`make validate` can return exit code 0 while Core remains incomplete because of assisted scenarios, such as a key revocation without a provided input. Assessment must therefore rely on the report and its verdicts, defined in [conformance 6](/en/docs/spec/conformance#6), rather than on the exit code alone.

A published conformance claim should identify the assessed scope and include the report, configuration with secrets removed and versions used. A [signed attestation](/en/docs/verify) allows the origin and integrity of one execution’s results to be verified; it does not certify the product.
